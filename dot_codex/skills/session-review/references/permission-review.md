# Phase 1: 権限レビュー 詳細手順

## Step 1: 手動承認の列挙

会話コンテキストを振り返り、以下を列挙する:

- ユーザーが「承認 (Allow)」したツール呼び出し
- ユーザーが「拒否 (Deny)」したツール呼び出し

各項目について記録: ツール種別 / 具体的な引数 / 承認or拒否

手動承認が一切なかった場合はこのフェーズをスキップ。

## Step 2: Codex の権限層を確認

承認が必要だった原因を sandbox、network、書込み対象、外部作用、破壊的操作に分類する。現在の `~/.codex/config.toml`、プロジェクト設定、AGENTS.md、管理ポリシーを読取範囲で確認する。秘密値は読み出さない。

永続的な権限緩和を既定案にしない。まずコマンドの縮小、読取専用化、対象パスの限定、既存 Plugin / connector の利用で解消できるか検討する。設定変更が必要なら、変更内容・影響範囲・理由を提示し、ユーザー承認後だけ適用する。

## Step 3: 最小権限の改善案を生成

手動承認された操作ごとに、最小の再利用可能な承認範囲または設定変更案を生成する。機密ファイル、破壊的操作、本番操作を恒久許可の候補にしない。

### shell コマンド

- 承認されたコマンドの実行ファイルと安全な固定サブコマンドまでを候補範囲にする
- 引数によって任意コード実行や破壊的操作が可能になる広すぎる prefix は提案しない
- 読取りで代替できるコマンドは恒久許可せず、読取手段を推奨する
- 既存承認でカバー済みなら「追加不要」と明記する

### ファイル書込み

- 対象リポジトリまたは特定ディレクトリまでに範囲を限定する
- `.env*`、鍵、認証情報、履歴、セッション、cache を候補から除外する
- ユーザー全体設定とプロジェクト設定のどちらが適切かを理由付きで示す

## Step 4: 提案の収集

Step 1〜3 の結果を SKILL.md 本体の一括提示フォーマットに渡す。
個別確認はしない（SKILL.md 本体で全フェーズまとめて1回確認する）。

## 適用時のルール

ユーザー承認後、Codex の現行設定仕様を確認して適用する際:

- 同種ルールの近くに配置（`Bash(...)` は既存 Bash の後、`Edit(...)` は既存 Edit の後）
- TOML 整合性と既存スタイルを保持する
- `.env.local` や `*.pem` など機密ファイルへのアクセス権限は絶対に提案しない
- `Edit` / `Write` は必ずセットで追加
- 管理ポリシーや deny と競合する候補は見送る
- `auth.json`、履歴、セッション、SQLite、Plugin cache の共有や chezmoi 管理を提案しない
