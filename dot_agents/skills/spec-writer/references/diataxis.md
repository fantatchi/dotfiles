# Diátaxis — 読者ニーズ別ドキュメント 4 分類

> 旧 documentation-writer スキル（2026-07-07 削除）から判断軸のみ吸収。
> 原典: <https://diataxis.fr/>

ドキュメントを「読者が何をしに来たか」で 4 種に分ける枠組み。1 つの文書に複数ニーズを混ぜると全読者にとって読みにくくなる、が中核の主張。

## 4 分類と判断軸

| 分類 | 読者の状態 | 文書の姿勢 | 典型例 |
|---|---|---|---|
| **Tutorial**（学習） | 初学者。何ができるか知らない | 手を動かさせ、成功体験まで導く。選択肢を見せない | Getting Started、オンボーディング演習 |
| **How-to**（課題解決） | 目的が明確。手順が知りたい | 前提を明示し、1 ゴール 1 レシピ。背景説明は最小 | 「X を Y に移行する」「Z を設定する」 |
| **Reference**（情報参照） | 仕様の正確な値・形式が知りたい | 網羅・正確・無駄なし。読み物にしない | API 仕様、設定キー一覧、CLI オプション |
| **Explanation**(理解) | なぜそうなっているか知りたい | 背景・設計判断・トレードオフを語る | アーキテクチャ解説、ADR の Context 節 |

## 使いどころの判定

- 「どの種類の文書が必要か」で迷う依頼（README 充実・ドキュメント整備・オンボーディング資料）は、まず読者とニーズを特定して 4 分類のどれかに割り当てる
- 既存文書が読みにくい場合、複数分類の混在を疑う（例: リファレンスにチュートリアル的な語りが混じる）→ 分割を提案
- 本スキルの主戦場（仕様書・ADR・C4）は Reference + Explanation に寄る。Tutorial / How-to が必要なら別ファイルに切り出す

## 章立てへの反映

- README は「入口ハブ」: 4 分類それぞれへのリンクを置く場所であり、全部を README に書かない
- 仕様書内で運用手順（How-to）が膨らんだら `docs/how-to/` へ分離
- ADR の Context/Consequences は Explanation として書く（手順を書かない）
