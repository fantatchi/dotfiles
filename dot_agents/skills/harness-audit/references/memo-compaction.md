# Phase 4: 判断メモ圧縮（自動適用）

`context.md` の `## 判断メモ` を仕分けして、定常サイズに保つ。`## 進行中の作業` の 14 日ローテーション（context-save が機械的に削除）とは違い、判断メモは「消す前に昇格すべきか」を判断する必要がある。そのため機械的な削除ではなく、判断を挟む処理として行う。

## 確認を取らずに適用する理由と安全策

2026-11-11 に確認制から自動適用へ変えた。判断材料は「memory・AGENTS.md・docs に既出かどうか」で、読めば照合できる。また、確認を挟んでも実際には全件そのまま承認されていた（memory `feedback_insurance-that-cant-protect` の「守れない保険」）。代わりに、誤りを戻せる形にする:

1. **削除・統合したエントリは作業ログへ退避してから context.md から外す**（context.md は多くのプロジェクトで git 管理外で、消すと戻せない）
2. **昇格は 1 回あたり 3 件まで**。4 件目以降は残置にして次回へ回す（MEMORY.md の索引は毎セッション読み込まれるので、誤った昇格は全プロジェクトに広がる）
3. **迷ったら残置**（誤削除より誤残存を選ぶ）

## 4 分類ルール

| 分類 | 条件 | 行き先 |
|---|---|---|
| **昇格** | 恒久 + 普遍（プロジェクトや時期を問わず効く）+ 未カバー | MEMORY に新規ファイル（`feedback_*.md` / `reference_*.md` / `user_*.md`） |
| **統合** | 恒久だが、既存の memory が同じテーマを持つ | 既存 memory ファイルに追記し、元のエントリは退避 |
| **削除** | AGENTS.md / docs / 既存 memory で既出、または期限付きの雑事で既に古い | 退避して context.md から外す |
| **残置** | 期限付きだが、再検討トリガー付きで「まだ生きている」判断 | context.md に残す |

## 手順

1. `{project-root}/.claude/context.md` の `## 判断メモ` を抜き出し、トップレベルのエントリを列挙する。次の **3 形式**をそれぞれ 1 エントリとして数える（数え方は context-save「判断メモの肥大アラート」と同じ）:
   - 先頭行が `- ` の箇条書き
   - `**見出し**:` の段落。**`:` の直前に括弧が入る `**見出し**（日付）:` の形もある**ので、`:` が直後に来る前提で数えると丸ごと落ちる
   - `### ` 見出し
   1 形式だけを数えると、その形式を使っていない context.md で 0 件になる
2. 各エントリを 4 分類に振り分ける。判定根拠（どの memory / AGENTS.md / docs に既出か）を必ず添える
3. **削除・統合の前に、既出と判定した実ファイルを開いて本当にカバーされているか確認する**
   - **「昇格済み」と書かれたエントリも、実ファイルがあるか確かめる。** 過去の session-review（Claude / Codex）が「MEMORY へ昇格した」と context.md に書き残していても、**書き込みが抜けていることがある**（2026-08-19 に ai-concierge で発覚: 前日の昇格 3 件が、全プロジェクトの memory を横断 grep しても見つからず、記録だけが「済んだ」と言っていた）。索引 `MEMORY.md` と実ファイルの両方を見て、無ければ**その場で作り直す**（3 件の上限には数えない）
4. **退避先の解決**: resolver `~/.claude/skills/shared/integrations.md` の `vault` を、参照規約の三分岐で判定する。(a) 未設定、または (c) 同期されていない場合は、**削除・統合に分類したものもすべて残置に切り替える**（退避できないなら外さない）
5. **退避の書き込み**: 削除・統合の対象を、作業ログに `## 退避した判断メモ` として書く
   - 書き出し先とファイル名は `~/.claude/skills/shared/vault-init.md` の 2〜3 節（`<vault>/20_log/YYYYMM/YYYYMMDDHHmmss_<タイトル>.md`）に従う。タイトルは `判断メモ退避-<プロジェクト名>`
   - 同じセッションの作業ログが既にあれば、新しく作らずにそのログへ追記する（`obsidian-log` の追記規則に合わせる）
   - 新しく作る場合の frontmatter は `project: "[[<プロジェクト名>]]"`、`source: claude-log`、`generation: 0`
   - 1 エントリごとに、**元の文面をそのまま**（改変・要約しない）と、`→ 削除（既出: <ファイル>）` / `→ 統合（先: <memory ファイル>）` の 1 行を書く
   - 書き込んだ後に読み直して、全エントリが入っていることを確かめる。**確かめられなければ context.md から外さない**
6. **昇格**: memory の frontmatter 規約（`name` / `description` / `metadata.type`）に従って新しいファイルを作り、`MEMORY.md` の索引に 1 行足す。本文には `**Why:**` / `**How to apply:**` を付け、関連するものを `[[name]]` でリンクする
7. **統合**: 既存の memory に追記する。同じことを二重に書かない
8. **context.md から外す**: 昇格・統合・削除したエントリを外し、残置だけを残す。書き込みは `~/.claude/skills/shared/multi-writer.md` の書き込み手順に従う
   - 書く直前に context.md を読み直す。仕分けた時点から `## 判断メモ` が他の writer に更新されていたら、自動での書き込みを止めて報告する
   - 書いた後の構造チェックでは、`## 判断メモ` 以外のセクション・未知の見出し・frontmatter が意図せず変わっていないことだけを見る
   - 削除が多いときは、セクション全体を置き換えるより、残置エントリを手を加えずに取り直し、1 回の部分置換で置き換える方が安全
9. **報告**: 1 行で `昇格 N（ファイル名）/ 統合 M / 退避 K / 残置 L → 退避先: <ログのパス>` と書く。上限で次回に回した件数があれば添える

## 注意

- 視覚設計など「スキル自身に属する知見」が context.md に残っていたら、昇格ではなくそのスキルの `references/` への移設を 報告に 1 行添えて提案する（自動では動かさない）
- 戻したいときは、退避ログから該当エントリを context.md の `## 判断メモ` へ書き戻す
