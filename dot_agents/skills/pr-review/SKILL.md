# PR Review

GitHub PR を再現可能な base/head SHA で検証し、根拠付きのレビュー草稿をローカルへ残す。GitHub へのコメント、レビュー送信、承認、マージ、push は行わない。

## 適用範囲と承認境界

- 対象は GitHub PR。URL、`owner/repo#123`、または現在のリポジトリに対する番号を受け付ける。
- 通常の「PR をレビューして」はルートエージェント単独で実行する。
- ユーザーが「ペルソナ」「複数観点」「サブエージェント」「委譲」「並列」を明示した場合だけ、`multi-persona-review` Skill を併用する。
- レビュー取得、`git fetch`、一時的な非破壊検証、ローカル草稿作成までを行う。認証情報は表示・記録しない。
- `gh pr review`、`gh pr comment`、`gh issue comment`、マージ、push などの外部書込みは、別途明示的に依頼されてもこの Skill 内では実行しない。草稿完成後に別作業として扱う。

現在の作業ツリーに未コミット変更があっても、対象 SHA の Git オブジェクトだけを読むため中断しない。既存変更を変更、stash、checkout、reset しない。

## 1. 対象を確定する

1. 対象階層の `AGENTS.md` と、存在するレビュー規約を読む。
2. 入力を解析する。
   - `https://github.com/<owner>/<repo>/pull/<number>`
   - `<owner>/<repo>#<number>`
   - 番号のみ。この場合は `gh repo view --json nameWithOwner` で現在のリポジトリを使う。
3. URL のリポジトリと現在のローカルリポジトリが一致することを `gh repo view` と remote で確認する。一致しない場合は、正しいローカル clone での実行を依頼して停止する。
4. `gh auth status` を安全に確認する。出力に認証情報を含めない。認証やネットワークで取得できない場合は、推測で続けずブロッカーを報告する。

対象リポジトリを clone し直したり、別リポジトリへ自動移動したりしない。

## 2. PR の証拠を取得する

GitHub API とローカル Git を使い、少なくとも次を取得する。

- PR 番号、URL、タイトル、本文、author、state、draft、base/head ブランチ。
- base/head の完全な commit SHA。
- changed files、additions、deletions、mergeable、mergeable_state。
- review、inline review comment、discussion comment。

API の PR 応答に含まれる `base.sha` と `head.sha` をレビューの固定点として記録する。PR 本文や既存コメントをペルソナへ渡す場合、重要な主張は要約せず原文を使う。要約する場合は「当方要約」と明示する。

必要な Git オブジェクトだけを取得する。worktree を変更するコマンドを使わない。

```text
git fetch --no-tags <remote> <base-branch> refs/pull/<number>/head
```

取得後、API の base/head SHA が `git cat-file -e <sha>^{commit}` で読めることを確認する。fork PR や remote 構成のため取得できない場合は、PR head の remote URL を確認し、明示的な SHA を fetch する。checkout、switch、pull はしない。

次を SHA 指定で調べる。

```text
git merge-base <base-sha> <head-sha>
git diff --find-renames --stat <base-sha>...<head-sha>
git diff --find-renames --name-status <base-sha>...<head-sha>
git diff --find-renames --check <base-sha>...<head-sha>
```

差分のファイルを作業ツリーから読まない。PR head は `git show <head-sha>:<path>`、base との比較は `git show <base-sha>:<path>`、参照検索は `git grep <pattern> <head-sha> -- <path>` を使う。

### 変更単位（Change Unit）の抽出

この PR が「何をしたか」を分解し、以降のすべての工程をこの ID で扱う。所見の主軸になるので証拠取得の一部として必ず行う。

- PR 本文の対応内容の箇条書きを**原文のまま** `C1..Cn` に採番する。要約しない（要約するとレビュー担当がそれを PR の主張と誤認し「本文と差分が不整合」型の偽陽性を作る）。
- `git diff --name-status <base-sha>...<head-sha>` の各ファイル・各 hunk を `C1..Cn` のどれかへ割り当てる。**どの C にも割り当たらない hunk が残ったら `CX: PR 本文に記載のない変更` として必ず 1 単位を立てる**。回帰はここに集中する。CX が空なら「空」と書く。
- 各 C について `git grep <pattern> <head-sha>` で**呼び出し元と到達する画面**を 1 行で控える。呼び出し元 0 件ならそう書く（severity の下げ止まり判断に直結する）。
- PR 本文の確認ポイントは各 C の「人が見るならここ」の素案に使う。
- 粒度は 3〜7 単位。分解に自信が無ければ、草稿の「この PR がやったこと」表の ID へ `（要確認）` を付けて依頼者の判断を仰ぐ。

## 3. レビュー観点を設計する

差分の性質、リスク、言語、ファイル境界から観点を選ぶ。固定の職種名ではなく、失敗モードを区別できる専門性にする。

- バグ修正: 真因との対応、回帰、境界値、再現テスト。
- 新機能: データ不変条件、認可、UX、後方互換性、テスト。
- リファクタリング: 挙動保存、呼出元、エラー経路、削除漏れ。
- 依存更新: breaking change、lockfile、peer dependency、供給網。
- CI・設定: secret 境界、権限、キャッシュ、失敗時挙動。
- migration・SQL: ロールバック、既存データ、ロック、段階展開。

明示的な並列レビュー依頼がある場合は `multi-persona-review` の指示を完全に読み、基本 3 人、独立性が十分なら最大 5 人へ自己完結した担当範囲を渡す。各子エージェントには base/head SHA、対象ファイル、確定事実、既存コメント、固有の問いを渡し、編集と外部書込みを禁止する。

子エージェントのアウトプット形式は次で固定する。

- 気づいた指摘は重要度順に全件出させる。「重大なものだけ」「保守的に」のような件数を絞る指示は出さない。絞りは 4 節の裏取り 1 パスに集約する。加えて「最も効きそうな指摘トップ 3」を明示させる。
- 2 節で作った変更単位表を**逐語で貼る**。指摘ごとに `対象変更: C2` のように ID を書かせる。どの C にも属さないと思うなら `対象変更: PR 外` と書かせる。判断を保留させない。
- **由来（新規か既存か）の判定はさせない**。「既存だから報告しない」という自主的な絞りを誘発し、件数を絞らせない設計に反する。変更前から在ると思ったものも必ず報告させる。由来の確定と隔離は 4 節の仕事だと明記する。
- 各指摘は `対象変更 / 場所 / 何が起きる / 再現手順 / 根拠` の 5 項目に固定する。散文で書かせない。字数でなく項目数で縛る。「根拠」＝ 逐語引用 + 到達経路は 4 節の裏取りの起点なので削らせない。削らせるのは経緯、背景説明、一般論。
- 再現手順は層を判定させる。`~/.claude/skills/shared/review-output-style.md` のルール 3（①画面のみ／②DevTools 必須／③複数セッション／再現しない）をプロンプトに貼り、指摘ごとに層を書かせる。①なら手順を番号付きで書かせる。ここで判定させておくと 8 節で書き直す手間が消える。
- 偽陽性リストは子エージェントへ渡さない。絞りは 4 節へ集約するという設計を崩さない。
- セキュリティ観点のペルソナを立てる回は、`~/.claude/skills/shared/security-review-exclusions.md` の 2 ブロックを逐語で貼る。要約しない。DoS、rust のメモリ安全、React の XSS、クライアント側の認可欠如といった定番の偽陽性がプロンプト段階で消える。

無応答のペルソナが出た場合は待ち続けない。その観点をルートエージェントが直接検証して 4 節へ進み、草稿のメモへ「○○ 観点はペルソナ無応答のためルートで代替検証」と、代替検証で実際に見た内容まで書く。

並列依頼がない場合は、同じ観点をルートエージェントが順に検証する。

## 4. 所見を裏取りする

発見した候補はすべてルートエージェントが head/base の実コードで裏取りする。子エージェントや既存 reviewer の主張だけで重要度を確定しない。

各候補について次を確認する。

1. PR が導入した問題か。base に既に存在する問題は捨てるか、8 節の「PR 外」表へ 1 行だけ隔離するかを毎回決める（詳細は書かない）。
2. 実行経路と呼出元が存在するか。型、設定、データモデルの不変条件で到達不能なら撤回する。
3. 既存テスト、型検査、lint、CI が防ぐか。機械的に確実に検出されるだけの指摘は原則除外する。
4. 既存の inline/discussion コメントと重複するか。重複は統合し、author の対応済み変更まで確認する。
5. 事実、推論、未確認の前提を分けられるか。
6. 反証条件または最小の追加検証を示せるか。

データの実在性など、コードと提供資料だけでは重要度が大きく変わる不変条件が残る場合は、ユーザーへ短い 1 問を出して回答を待つ。質問前に、コードから確認可能な範囲は調べる。草稿には前提の出所を記録する。

1 つの原因に複数の症状がある場合、症状ごとに発生条件、頻度、害、再現方法を分けてから重要度を付ける。修正の容易さだけで重要度を上げない。

重要度を付ける前に、各所見へ 3 値の verdict を付ける。REFUTED 側に立証責任を課すのが目的。

- CONFIRMED: 発火する入力・状態と、その結果どう間違うかを名指しできる。
- PLAUSIBLE: 機構は実在するがトリガが不確実（タイミング、環境、データ依存）。
- REFUTED: コードから構成できるときだけ。①事実誤認（該当行を引用）②型・定数・不変条件で不可能（それを提示）③この diff 内で既に処理済み（ガード行を引用）④観測可能な影響のない純スタイル。

既定は PLAUSIBLE。「speculative だから」「ランタイム状態に依存するから」を REFUTED の理由にしない。並行性レース、エラーハンドラ・コールドキャッシュ・欠落オプショナルのような稀だが到達可能なパス、falsy-zero、境界の off-by-one、リトライ嵐・部分失敗は現実的な状態として扱う。ここを緩めると、下の抑制ルールと合わさって実バグまで消える。抑制ルールを適用する場合も REFUTED と同じ立証責任がかかる。

CONFIRMED と PLAUSIBLE を残して重要度へ進み、REFUTED は撤回記録へ回す。

verdict と同じパスで**由来**も確定する。verdict が「実在するか」なら、由来は「誰のせいか」を決める。読み手の「これは本当にこの PR のせいか」に答えるための項目。

- **①新規機能の欠陥**: この PR が足したコードの中の欠陥。追加行そのものの引用で足りる。
- **②新規回帰**: 変更前は成立していた挙動が、この PR で崩れた。**`git show <base-sha>:<path>` の逐語引用が必須**。示せないなら①か③へ倒す。
- **③既存債務**: 変更前から在り、この PR は触っていない。8 節の「PR 外」表へ隔離し、詳細ブロックを書かない。例外として「この PR が触った関数の未変更行」（`③*`）は本文に残し、通常どおり重要度を付ける。
- **④PR 目的の未達**: PR 本文が主張する狙いに実装が届いていない。本文の該当箇所の逐語引用と、届いていない実体の引用の 2 点が要る。

②は「本文が触れていないのに壊れた」ものに限る。PR 本文が意図として明記している挙動変化は仕様変更であって回帰ではない。由来が決まらない所見は①に倒さず `判定不能` と書き、重要度を 1 段下げる。

重要度はユーザー共通規約に従う。加えて由来を次のとおり反映する。

- ②新規回帰は、到達経路（呼出元・画面）が現存するなら MIDDLE 未満に下げない。到達経路が無いなら LOW でよいが「前提が変われば復活するもの」に 1 行残す。ただし下げ止まりが効くのは機能・データ・操作可能性に影響する②だけで、見た目だけの変化は LOW でよい。
- ③既存債務は原則 LOW とし「PR 外」表へ隔離する（`③*` は除く）。隔離した件数を結論の 1 行に足す。
- ④PR 目的の未達は、本文の逐語引用を根拠に持つ限り降格しない。PR が自称した完了条件の話なので、実害の狭さを理由に下げない。

- `CRITICAL:` セキュリティリスク、データ損失、本番障害。
- `HIGH:` 機能不全、重大な性能問題、大きな設計問題。
- `MIDDLE:` 潜在的バグ、保守性、ベストプラクティス、文書不足。
- `LOW:` 軽微な改善、スタイル、推奨事項。

各所見へ 0〜100 の確信度を付け、原則 60 未満は確定指摘に含めない。CRITICAL 候補は低確信でも、理由と追加検証を保留事項へ残してよい。

偽陽性として落とす典型は `~/.claude/skills/shared/review-false-positives.md` に集約されている（`multi-persona-review` と共通の SSOT）。裏取りの前に必ず一読する。計測のない `useMemo` などの性能最適化、データモデル上発生しない状態への防御コード、一時的と明示された mock の将来構造、実行経路が示せない一般論上の脆弱性は、推測だけで重要度を上げない。

裏取りで前提が崩れた所見は撤回し、verdict: REFUTED として撤回記録へ残す。実害の範囲が想定より狭いと確認できた所見は HIGH→MIDDLE、MIDDLE→LOW へ降格する（verdict は PLAUSIBLE のまま残る）。

アクセシビリティやプロジェクト固有の除外は、適用される `AGENTS.md`、仕様、レビュー方針に従う。存在しない Claude MEMORY のキーを規約として仮定しない。

## 5. ギャップを掃討する

3 節の並列は「各ペルソナが自分の観点で見つけたもの」で打ち止めになり、収束後の穴が残る。並列レビューを行った回は、掃討専用のサブエージェントを 1 体だけ起動する。

1. 4 節で確定したリスト（ファイル:行 + 一行要約）を渡し、そこに無い欠陥だけを探す fresh reviewer として起動する。
2. プロンプトに次の制約を必ず入れる。
   - 既にリストにあるものの再確認、再導出はしない。仕事は穴埋めだけ。
   - 新規候補は最大 8 件。無ければ空で返す。水増ししない。
   - 狙い目: 移動・抽出でガードやアンカーが落ちたコード／二軍の footgun（デフォルト引数が 1 回だけ評価される、ハッシュの非決定性、ロックスコープの縮小、副作用のある述語メソッド）／テストの setup・teardown 非対称／config デフォルトの反転。
3. 返ってきた候補は 4 節の裏取り、verdict、重要度を同じ手順で通す。掃討結果を無検証で所見に載せない。
4. 差分 100 行未満の機械的変更ではスキップしてよい。スキップした場合もその旨を草稿のメモへ 1 行残す。

## 6. 競合と base 移動を確認する

GitHub が競合を報告する場合、merge-base から head 側と base 側の両方で変更されたファイルを特定する。コード欠陥とは別に、解消時に失われ得る base 側の挙動・テスト・設定を受け入れ条件として列挙する。

草稿作成前に PR API を再取得し、base/head SHA が開始時から変わっていないか確認する。

- head SHA が変わった場合: 古い差分の所見を確定せず、新しい head を取得してレビューを更新する。
- base SHA だけが変わった場合: 新しい base を取得し、diff、競合、採用所見を再確認する。
- 再取得中にも SHA が動き続ける場合: 確認した SHA と時刻を明記し、レビューが暫定であることを報告する。

## 7. 非破壊的な検証を行う

差分に対応する既存の lint、型検査、テストを選ぶ。現在の worktree が head SHA と一致し、既存変更へ影響しない場合はそのまま実行できる。

一致しない場合、必要性が高く、依存関係を追加取得せず実行できるときだけ、`mktemp -d` 配下へ detached worktree を作って検証する。自分で作成した一時 worktree だけを後始末する。パッケージ導入、lockfile 更新、外部環境への接続、本番向け切替は行わない。

検証できない場合は、未実行のコマンドと理由を草稿へ記録する。テスト未実行を成功として扱わない。

## 8. ローカル草稿を作る

`.claude/reviews/` に次の名前で Markdown を新規作成する。

```text
pr-<number>-<branch-last-segment>-<YYYY-MM-DD>.md
```

branch 部分は安全な英数字・ハイフンへ正規化する。同名ファイルが既に存在する場合は上書きせず、SHA の短縮形または連番を加える。編集には `apply_patch` を使う。

書く前に `~/.claude/skills/shared/review-output-style.md` を読む（`multi-persona-review` と共通の出力規約 SSOT）。草稿は初見のジュニアエンジニアが読み通せる密度にするのが要件で、4 つのルール — ①1 指摘 4 項目・6 行以内 ②専門用語は初出で 1 行言い換え ③再現手順は層を判定して必ず書く ④削った詳細は「詳細を聞けば出せる項目」へ見出しだけ送る — をすべて適用する。

草稿には次を含める。

```markdown
# PR #<number> レビュー所見

- URL / タイトル / author / base / head
- base SHA / head SHA / merge-base / レビュー日時
- 規模 / state / mergeability

## 結論

<3 行以内。1 行目でブロッカーの有無を言い切る。件数は「CRITICAL0 / HIGH1 / MIDDLE9 / LOW12 ＋ PR 外 3」のように 1 行>

## この PR がやったこと

| ID | やったこと | 差分の場所 | 人が見るならここ | 指摘 |
| --- | --- | --- | --- | --- |
| C1 | <PR 本文の原文。長ければ 40 字で切る> | `path/to/hook.ts` ほか 2 | <動作確認の入口を 1 行> | LOW-1 / LOW-2 |
| C2 | <同上> | `path/to/file.tsx:112-283` | <入口を 1 行> | HIGH-1 / MIDDLE-1 / LOW-3 |
| CX | PR 本文に記載のない変更 — <差分から 1 行> | <場所> | <入口> | なし |

CX の行は必ず置く（本文の箇条書きに割り当たらなかった hunk。空なら「やったこと」欄に「空」と書く）。分解に自信が無ければ ID へ `（要確認）` を付ける。

## 直すなら効く順

1. **<PREFIX-N>**（<C-ID>） <1 行>
2. **<PREFIX-N>**（<C-ID>） <1 行>
3. **<PREFIX-N>**（<C-ID>） <1 行>

（重要度順とは限らない。実害 × 修正コストで並べる）

## 指摘一覧
```

構造の要点。

- スコープ節は置かない。必要な情報はメタ行と結論に入る。
- **指摘は重要度順の 1 本のフラットな並びにする**。変更単位でグループ化しない（グループ化すると HIGH が草稿内に散らばり、「まず何を直すか」を掴むのに全体を読むことになる）。
- **「この PR がやったこと」を結論の直後に置く**。この節が「草稿単体で確認作業に入れるか」を決める（無いと読み手は結局 PR 本文を開くことになる）。各セルは 1 行で、ここで指摘の内容を説明し始めない。
- **「人が見るならここ」列は指摘が 0 件の変更単位でも必ず埋める**。「ここは見たが指摘なし」が伝わるのがこの列の役目。呼出元・到達する画面は重要度判断の材料なので草稿には出さず、結論を左右したものだけ検証節へ。
- **指摘一覧の「何が起きる」列は、指摘見出しの文言をそのまま再掲する**。新しい説明文を書かない（索引表は本文と二重に書く失敗を招きやすいので、文言を共有させて防ぐ）。
- **変更単位は指摘見出しの `（C2）` と指摘一覧の列の 2 箇所だけで表現する**。verdict 行に載せるのは由来（①〜④）だけで、行は増やさない。指摘本文で「これは本 PR が新設した回帰で」と説明し始めない。1 指摘 6 行を守る。
- **「直すなら効く順」は重要度順とは限らない**。指摘一覧が重要度順になったぶん、この節は実害 × 修正コストで見た推奨順として役割を分ける。
- ③既存債務は「PR 外」表に 1 行だけ置き、詳細ブロックを書かない。
- verdict 行は見出し直下に置き、根拠は 1 行に収める。
- REFUTED は本文に書かない。「詳細を聞けば出せる項目」へ `REFUTED N 件それぞれの撤回理由` の 1 行で送る。ただし前提が変われば復活するものは、復活条件だけ 1 行を「PR 外」節の末尾に残す。
- メモには `掃討: 新規 N 件`（またはスキップ理由）を 1 行記録する。
- 機構の解説、ルール実装の引用、経緯、他案の比較は草稿に書かない。すべて「詳細を聞けば出せる項目」へ見出しだけ送る。ただしその回のレビューの結論を左右した事実（実行して分かったこと）は検証節に 1 行で残す。

所見は重要度順、同じ重要度では影響度順に並べる。所見がなければ「ブロッカーなし」と明記し、確認範囲と残存リスクを示す。良い点は根拠があるものだけを書く。

context、progress、tasks は変更しない。CRITICAL または HIGH の投稿判断が残る場合だけ、別途タスク化を提案する。
