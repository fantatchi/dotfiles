# Multi-Persona Review

独立した複数の専門観点を並列で走らせて、単独レビューでは見落とす死角を潰すスキル。

## このスキルが解く問題

1 人のレビュアー（メインエージェント）は **1 つの観点に固着しがち**。特に以下のバイアスを生む:

- **可用バイアス**: 直前に読んだ知識・経験で物語を組み立て、それで仮説確定
- **整合性バイアス**: ある仮説で全観測が説明できると、他の仮説が同じく説明できることに気づきにくい
- **専門領域偏り**: バックエンド側の人間が UI/UX や運用観点を軽視するなど

並列で違う専門観点を走らせると、各エージェントが異なる前提で同じ素材を読むため、**整合的物語ではなく区別可能性で仮説評価**できる。

## 使うべき時 / 使うべきでない時

**使う**:
- インシデント対応の post-mortem で死因仮説を評価したい
- 重要な設計判断（アーキテクチャ選択 / migration 戦略）の見落とし潰し
- runbook / 仕様書を本番投入前に第三者目線で監査
- 自分が立てた仮説を「整合的物語に飛びついていないか」検証したい
- 3 つ以上の独立した専門観点に分解できる

**使わない**:
- 単純なバグ修正・1 ファイル編集
- ユーザーが「軽く見て」「急いでる」と言っている
- 並列化の余地が小さい（1 観点で十分なタスク）
- 破壊的操作を伴う作業（読取専用前提のスキル）
- **自分（メインエージェント）の作業を検証・ダブルチェックする目的**（自己修正は素で働くため、二重化はコスト増にしかならない）。本スキルの価値は「別の専門観点を足すこと」であって「同じ観点をもう一度回すこと」ではない

## 実行手順

### Step 1: ペルソナ設計（3〜5 人）

レビュー対象を分析し、**観点が独立な専門ペルソナ**を 3〜5 人選ぶ。

設計の指針:

- **専門領域が重ならない**: 「バックエンド」「フロントエンド」「インフラ」のような表層分類より、「Python 並行性」「Windows プラットフォーム」「SRE 故障診断」のように **解くべき問題に効く専門性** で切る
- **3 人を基本、複雑なら 5 人まで**: 2 人だと観点不足、6 人以上だと統合コストが見合わない

ペルソナの典型例:

| 領域 | ペルソナ例 |
|---|---|
| 障害分析 | Windows プラットフォーム / Python 並行性 / SRE 故障診断 |
| 設計レビュー | アーキテクト / セキュリティ / ペネトレ / SRE |
| コードレビュー | シニア開発 / セキュリティ / テスト設計 / アクセシビリティ |
| runbook 監査 | 運用エンジニア / インシデント対応 / 新人視点 |

### Step 2: 共通プロンプトのテンプレート設計

各ペルソナに渡すプロンプトに **必ず含める要素**:

1. **ペルソナ定義**: 「あなたは XX エンジニア (XX に詳しい人) です」
2. **状況概要 (確認済の事実)**: 何が起きていて、何が確定済みか。**仮説や推測は分けて書く**（先入観を植え付けないため）
   - **確定事実と規約は原文（逐語）で渡す**。要約するとペルソナが「対象側の主張」と誤認して偽陽性を生む（PR #19 の実例、memory `[[pr-review-persona-prompt-verbatim]]`）。字数を詰めたい場合のみ要約し、その旨を「（当方要約）」と明示する
   - 自分が**既に機械的に確定させた結果**（全数突合の出力など）も確定事実として渡す。渡さないとペルソナが同じ照合をやり直し、しかも手作業なので当方より精度が落ちる
3. **前提の参照ポイント**: 読むべきリポジトリ / ファイル / コミット / ログ
4. **レビューしてほしい観点 (4〜6 個の番号付き質問)**: ペルソナ固有の専門知識から答えてほしいこと
5. **アウトプット形式**: 気づいた所見は **重要度順に全件列挙** させる（「重大なものだけ」「保守的に」のような件数を絞る指示は出さない。絞り込みは Step 3.5 / 統合側の 1 パスに集約する）。そのうえで「最も効きそうな対策トップ 3」を箇条書きで明示。字数の目安 (500〜800 字) は各所見の説明文に掛けるもので、所見の件数を削る根拠にしない
6. **読み取り専用の指示**: コード変更・設定変更しないこと、Read / Glob / Grep / WebSearch を必要に応じて使ってよい

**重要な書き方のコツ**:

- ❌「真因を特定して」→ 結論の押し付けに見える
- ✅「残仮説 ① ② ③ のうち、あなたの専門知識から見て蓋然性順位はどうか? それぞれの追加検証手段を 1〜2 個ずつ」→ 専門知識を引き出す質問

- ❌「コードを直して」→ スキルの読取専用前提に反する
- ✅「最も貢献度が高そうな対策トップ 3 を箇条書きで」→ 提案を集めるだけ

### Step 3: 並列起動

`Agent` ツールを **同一の assistant メッセージ内** に N 回呼ぶ。Claude Code は同一メッセージ内の独立したツール呼出を並列実行するため、N 人分のレビューが同時に走る（直列の 1/N 時間で完了）。

要点:

- **subagent_type**: 基本 `general-purpose`（read/write 全権付きだが、プロンプトで読取専用に縛る）。コード探索が中心なら `Explore` も選択肢
- **依存関係**: ペルソナ間に依存がない（A の結果を B が見る必要がない）こと。これは並列化の前提。横断的な議論はメインエージェント側で Step 4 で行う
- **prompt の自己完結性**: 各 prompt は他のペルソナのことに言及しない（各エージェントは互いを知らない）。「他のレビュアーと違う観点で」のような相対的な指示は不可
- **description**: Agent 呼出の `description` には「<ペルソナ名 short> review of <対象 short>」のような短い識別子を入れる（並列実行のログで判別しやすい）

### Step 3.5: 確信度フィルタ（偽陽性の機械的除外、任意）

各ペルソナの所見をそのまま統合すると、蓋然性の低い指摘・偽陽性が Tier 分類に紛れ込む。統合の前に各所見へ確信度スコアを付け、閾値未満を落としてから Step 4 に渡す。公式 `/code-review` の confidence scoring を汎用レビュー向けに一般化したもの。

**原則: 絞りは finder（ペルソナ）側でなく、この後段 1 パスに集約する**。レビュアーに「重大なものだけ」「保守的に」と指示すると指示どおり報告量そのものが減り、拾えたはずの実在の問題を落とす。Step 2-5 で全件列挙させているぶん、本ステップの重要度は相対的に高い。

**やること**:

1. 各ペルソナが挙げた所見を粒度を揃えて列挙（重複は 1 件に統合）
2. 各所見に 0–100 の確信度スコアを付ける。**既定はメインエージェントのインライン採点**。採点専用 Agent（軽量モデル可、Haiku 等）への分離は、所見が多く（目安 10 件超）かつ重大判断を含むときに限る（採点者がレビュアーと同一だと甘くなるという利点はあるが、少数の所見に 1 件 1 体を割くのは委譲コストに見合わない）
3. スコア < 60 を既定閾値として除外（重大カテゴリのみ閾値を下げる調整可）

**確信度ルブリック**（採点者に逐語で渡す）:

- **0–25**: 軽い精査で崩れる。偽陽性、または既存（変更前から存在する）問題
- **26–50**: 実在は確認できたが nitpick / 低頻度。相対的に重要度が低い
- **51–75**: 裏取り済みで実務に効く。現状の前提では不十分と確認できた
- **76–100**: 証拠が直接裏付ける。高頻度で実害が出る

**偽陽性として落とす典型**（コードレビュー文脈の例、汎用では読み替え）:

- 変更前から存在する既存問題（今回の対象が導入したものでない）
- linter / typechecker / コンパイラ / CI が機械的に拾うもの
- シニアが指摘しない衒学的 nitpick
- 意図的な変更・対象の本筋に直結する挙動変化
- 対象が触れていない箇所への指摘
- **プロジェクトの過去実測記録で既に反証済みの指摘**: 採点前に context.md 判断メモ / MEMORY / docs の実測値と突き合わせる。ペルソナは過去セッションの検証履歴を知らないため、決着済みの論点を再提起しがち（実例: RF n_jobs 非決定性の指摘が過去実測 Brier ~1e-9 で反証済みだった、2026-07-07 toto-predictor）

このステップは任意。指摘が少数で偽陽性リスクが低いとき（軽量タスク）はスキップして Step 4 に直行してよい。

### Step 4: 統合判断（メインエージェント）

3〜5 人の所見が返ってきたら、メインエージェントが統合する。やること:

0. **メイン側で実コードを開いて裏取りする**（Step 3.5 の採点と対になる工程）。指摘されたファイル・行を実際に `Read` し、周辺を `Grep` で確認してから採否を決める。ペルソナの所見文だけで Tier 分類まで進めない。これは「自分の作業の再検証」ではなく**他エージェントの主張の一次確認**で、`pr-review` の Phase 4 と同じ位置づけ（finder 側で絞らせない設計とセット）。各ペルソナに「ファイルパス:行番号と逐語引用を必ず添える」と要求しておくと、この裏取りが機械的に回る
1. **重要な新発見を抽出**: 各ペルソナが独立に挙げた指摘のうち、メイン側で見落としていた論点を 3〜5 つピックアップ。表組みで提示
2. **仮説の再評価**: 各ペルソナが提示した残仮説を統合し、蓋然性を整理。**唯一統一的に説明できる仮説**があれば最有力として明示
3. **推奨アクション**: 各ペルソナの「対策トップ 3」を統合し、**Tier 1 (即時) / Tier 2 (短期) / Tier 3 (構造変更)** に分類して提示
4. **Tier 3 の判断保留**: 観測なしで構造変更を入れない原則を遵守。「証拠取得後に判断」と明示

### Step 5: ユーザーへの提示

統合所見を以下の構造で提示:

```
## 統合所見 — 重要な新発見 N 個

### 1. <発見タイトル>（誰の指摘）
<内容>

### 2. ...

---

## 推奨実装プラン（優先順）

| 案 | 内容 | 時間 |
|---|---|---|
| α | Tier 1 + Tier 2 | NN 分 |
| β | Tier 1 のみ | NN 分 |
| γ | 全部 (Tier 3 含む) | NN 分 |

推奨: <推奨案> (理由)。どれで進めますか?
```

ユーザーの選択を待ち、承認された範囲のみ実装に進む。

## よくある失敗と回避策

| 失敗 | 回避策 |
|---|---|
| ペルソナの専門領域が重複し似た所見が並ぶ | 「バックエンド」のような表層分類ではなく、解くべき問題に効く細粒度の専門性で切る（例: 「フロントエンド」→「アクセシビリティ」「パフォーマンス」「i18n」） |
| 各ペルソナへの状況説明に「結論」を書いてしまい誘導 | 状況概要は「確定事実」と「仮説」を明確に分けて書く。仮説は「現時点でこう推測している」と明示し、ペルソナに評価を任せる |
| アウトプットが長すぎて統合コストが膨らむ | 字数の目安（500〜800 字）は**各所見の説明文**に掛ける + 「最も効きそうな対策トップ 3」を箇条書きで要求。所見の**件数**は絞らせない（絞りは Step 3.5 に集約） |
| 統合せず所見をそのまま並べて終わる | Step 4 の統合は必須。新発見抽出 + 仮説再評価 + Tier 分類で初めて価値が出る |
| 偽陽性・低蓋然性の所見を採点せず統合してしまう | Step 3.5 の確信度フィルタで 0–100 採点し閾値未満を除外してから統合する。採点者はレビュアーと分離（甘くなるのを防ぐ） |
| Tier 3 の構造変更を観測なしで投入してしまう | 「証拠取得後に判断」を原則として Tier 3 は保留、ユーザー判断を待つ |
| 統合判断で「もう 1 観点欲しかった」と感じる | 追加で 1 人だけ起動するのも可（コスト増を許容するなら）。ただし最初のペルソナ設計時に専門領域カバレッジを意識するのが本筋 |

## 関連スキル / 参考

- `~/.claude/CLAUDE.md` の **Agent Teams の使い所** セクション: 1 セッション 1 チーム制約のある TeamCreate 機構との比較。本スキルはより軽量な並列 Agent パターン
- `session-review`: セッション完了時の振り返りスキル。本スキルで集めた所見を session-review の更新候補として活かせる
- `pr-review`: **GitHub PR が対象ならこちらを使う**。ブランチ切替・最新化、Copilot / discussion コメント取得、ペルソナ並列（本スキルの Step 2-3 を内部で参照）、実コード裏取り、`.claude/reviews/` への所見草稿出力までを一気通貫で行う。本スキルは PR に限らない汎用レビュー（障害分析・設計・runbook 等）向け
- `codex-fix-loop`: 指定した対象の**コード全体**（git 不要）を **Codex（別モデル）** に 1 次レビューさせ、critical / high が 0 になるまで反復する。本スキルが Claude 内の複数ペルソナで観点を分けるのに対し、あちらはモデルそのものを変えて収束させる。読取専用の所見が欲しいだけなら本スキル、修正まで回したいならあちら
- 公式 `/code-review` plugin（`~/.claude/plugins/marketplaces/claude-plugins-official/plugins/code-review/`）: PR 差分専用の自動レビュー（confidence scoring + 80 閾値 + gh コメント投稿）。**純粋な PR/コード差分レビューはこちらを直接使う**のが正解で、本スキルは障害分析・設計・runbook 等の汎用レビュー向け。Step 3.5 の確信度フィルタは code-review の confidence scoring を汎用化して取り込んだもの
