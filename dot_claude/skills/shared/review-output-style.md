# レビュー出力の書き方（共通ルール）

`multi-persona-review` と `pr-review` が共有する出力規約の SSOT。所見をユーザーが読む形にするときは、この 4 つのルールに従う。

**このファイルが解く問題**: レビューの所見は放っておくと「機構の解説」「経緯」「一般論」で膨らみ、初見で読む気を失う密度になる。実際に 2026-08-28 の PR #850 レビューで、ブロッカー 0 件の PR に対して所見ファイルが 1 万字を超えた。読まれない所見は書いていないのと同じなので、**長さではなく構造で縛る**。

---

## ルール 1: 1 指摘 = 4 項目・見出し込み 6 行以内

各指摘は次の 4 項目だけを書く。散文で書かない。

```markdown
### MIDDLE-1: <30 字以内で「何が問題か」を言い切る>
- **場所**: `path/to/file.tsx:123`
- **何が起きる**: <1 行>
- **再現手順**: <ルール 3 に従う>
- **直し方**: <1 行。工数感が非自明なら「1 行」「1 ファイル追加」程度を添える>
```

書かないもの: 経緯、機構の詳細解説、「なぜそう設計されているか」の考察、関連する一般論、他の選択肢の比較。**これらは書かずに捨てるのではなく、ルール 4 の「詳細を聞ける項目」へ見出しだけ送る。**

`verdict`（CONFIRMED / PLAUSIBLE）を使うスキルでは、見出し直下に 1 行だけ足してよい（合計 7 行）。

## ルール 2: 専門用語は初出で 1 行言い換える

読み手はそのコードベースに詳しいとは限らない。**フレームワーク・ライブラリ固有の語、その PR で導入された造語、パターン名**は、初めて出したところで 1 行だけ平易に言い換える。2 回目以降は説明しない。

- ❌ 「derived-value-sync パターンの違反を render-phase setState へ変換」
- ⭕ 「『prop が変わったら state を作り直す』処理を、`useEffect` の外（レンダー中）へ移した」

判定に迷ったら「その語を知らない人が、この 1 行だけ読んで何が壊れるか分かるか」を基準にする。分からないなら言い換える。

**略号・記号も開く**: `#843` のような番号だけの参照は「#843（ダイアログ初期化の解消）」のように中身を 1 語添える。

## ルール 3: 再現手順は「層」を判定してから書く（省略しない）

指摘ごとに、まず次の 3 層のどれかを判定する（判定の元ネタは MEMORY `feedback_pr_review_repro_tiers`）。**判定結果は必ず所見に書く。「再現手順」の項目を空欄にしたり削ったりしない。**

| 層 | 意味 | 書き方 |
|---|---|---|
| **①画面のみ** | 通常のユーザー操作だけで再現する | **手順を必ず番号付きで書く**（下記フォーマット）。省略不可 |
| **②DevTools 必須** | 開発者ツール・ネットワーク遮断・特定データ投入が要る | 「②DevTools 必須」と明記し、何を仕込むかを 1 行 |
| **③複数セッション** | 2 つのブラウザ・別ユーザー・時間差が要る | 「③複数セッション」と明記し、必要な条件を 1 行 |
| **再現不可** | コード上の問題で画面に出ない（保守性・テスト不在・コメント誤りなど） | **「画面からは再現しない（理由）」と 1 行で書く**。空欄にしない |

①の書式（これ以上詳しくしない）:

```
1. <画面名>を開く
2. <操作>
3. <操作>
→ <観測される誤り。期待値も 1 行で>
```

**①なのに手順を書かないのが最悪**。読み手が「自分で確かめられるのか」を判断できなくなり、指摘全体の信用が落ちる。逆に①でないものに手順をでっち上げるのも同じくらい悪いので、層の判定を先にやる。

## ルール 4: 「詳細を聞ける項目」を必ず置く

削った詳細は消すのではなく、**見出しだけを一覧にして残す**。読み手が「これは気になる」と思ったものだけ、その場で聞けばセッション中に展開できる。

```markdown
## 詳細を聞けば出せる項目

聞かれたら展開します（所見には結論だけ書いています）。

- MIDDLE-2 の「到達経路が特定できない」をどう調べたか（grep した対象と、モーダルの inert 判定の根拠）
- REFUTED 6 件それぞれの撤回理由
- 破棄されるレンダーで実際に何が二重実行されるか
```

- **1 項目 1 行**。ここで説明を始めない
- **REFUTED（撤回した指摘）は原則ここへ送る**。撤回理由の詳細は本文に要らない。ただし「前提が変われば復活する」ものは、復活条件だけ 1 行で本文に残す
- 所見ファイルを書いた後にセッションが切れても答えられるよう、**根拠にした実行コマンド・ファイルパスは「検証」節に残しておく**（詳細の説明文は残さなくてよい）

## 全体の分量の目安

| 節 | 目安 |
|---|---|
| 結論 | **3 行以内**。ブロッカーの有無を最初の 1 行で言い切る |
| 直すなら効く順 | 3 件・各 1 行 |
| 指摘一覧（表） | 1 指摘 1 行 |
| 各指摘 | ルール 1 のとおり 6 行以内 |
| 検証 | 実行したコマンドと結果だけ。考察を書かない |
| 詳細を聞ける項目 | 1 項目 1 行 |

**指摘の件数は絞らない。** 短くするのは 1 件あたりの説明であって、拾う件数ではない（件数を絞ると実在の問題を落とす。絞り込みは裏取りフェーズの 1 パスに集約する既存設計を崩さない）。

## よくある失敗

| 失敗 | 回避策 |
|---|---|
| 「何が起きる」に機構の説明を書いて 5 行になる | 症状だけ書く。機構はルール 4 へ送る |
| 再現手順を「操作すれば分かります」で済ませる | ①なら番号付きで書く。書けないなら層の判定が間違っている |
| 保守性の指摘に無理やり再現手順を作る | 「画面からは再現しない（コメントの記述誤りのため）」と書けばよい |
| 詳細を全部消してしまい、後から聞かれても答えられない | 検証節に実行コマンド・ファイルパスを残す。消すのは説明文だけ |
| 用語の言い換えを毎回書いて冗長になる | 初出 1 回だけ |
| 件数を減らして短くする | 減らすのは 1 件あたりの行数。件数は据え置き |
