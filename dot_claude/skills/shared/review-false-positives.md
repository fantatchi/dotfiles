# レビュー偽陽性カタログ（SSOT）

レビュー所見を採否判定するときに**落とす典型**の一覧。
`pr-review` の Phase 4（裏取り）と `multi-persona-review` の Step 3.5（確信度フィルタ）が共通で参照する。

**適用位置は後段のみ。** finder（ペルソナ / サブエージェント）の prompt にこのリストを入れてはならない。
レビュアーに「重大なものだけ」「保守的に」と指示すると報告量そのものが減り、拾えたはずの実在の問題を落とす。
絞りは後段 1 パスに集約する。

## 落とす典型

1. **変更前から存在する既存問題** — 今回の対象が導入したものでない
2. **バグに見えてバグでないもの** — 読み違い。該当行を引用して確認する
3. **シニアが指摘しない衒学的 nitpick**
4. **linter・型検査・コンパイラ・CI が機械的に拾うもの** — import 漏れ / 型エラー / 壊れたテスト / 整形 / 改行のようなスタイル。
   これらは CI で別途走る前提でよく、**確認のためにビルドや型検査を自分で回す必要はない**
5. **一般品質の指摘** — テストカバレッジ不足、漠然としたセキュリティ懸念、ドキュメント不足。
   ただし **CLAUDE.md / AGENTS.md が明示的に要求している**場合は対象内（その場合はルール原文を引用する）
6. **コード側で明示的に抑止済み** — lint ignore コメント、`// intentional` 等で作者が判断を記録している箇所
7. **意図的と思われる機能変更** — 対象の本筋に直結する挙動変化
8. **author が変更していない行への指摘**
   - 例外: **触られた関数の未変更行**は対象内（その PR がバグを再露出させた / 直しそこねた、と言えるため）。
     この例外は公式 `/code-review` の Angle A に由来する
9. **プロジェクトの過去実測記録で反証済みの指摘** — 採否判定の前に `context.md` の判断メモ / MEMORY / docs の実測値と突き合わせる。
   ペルソナは過去セッションの検証履歴を知らないため、決着済みの論点を再提起しがち
   （実例: RF `n_jobs` 非決定性の指摘が過去実測 Brier ~1e-9 で反証済みだった、2026-07-07 toto-predictor）

## 落とす側にも立証責任がある

このリストは「落としてよい形」を定義するもので、**落とす理由の免罪符ではない**。
実在しうる欠陥をリスト 1〜9 のどれかに当てはめて消すときは、
`pr-review` Phase 4 の REFUTED と同じ水準の根拠（該当行の引用 / 不変条件の提示 / ガード行の引用）を所見に残す。

特に「speculative だから」「ランタイム状態に依存するから」は**落とす理由にならない**。
並行性レース、エラーハンドラ・コールドキャッシュ・欠落オプショナルのような稀だが到達可能なパス、
falsy-zero、境界の off-by-one、リトライ嵐・部分失敗は現実的な状態として扱う。
