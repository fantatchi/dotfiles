# tasks.md フォーマット仕様

タスク管理スキル（`gtd-add`, `gtd-list`, `gtd-done`）および `context-save`, `context-load` が共通で参照するフォーマット定義。

## 2 つのストア

タスクは役割の異なる 2 つのストアに分かれる。**両者の間にスキル間の依存は無く**、片方だけの環境でもそれぞれ完結して動く。

| ストア | 実体（出典） | 中身 | writer | reader |
|---|---|---|---|---|
| **捕捉箱** | resolver `task_store`（既定 `~/ObsidianVault/00_meta/tasks.md`） | どのプロジェクトの話か決まっていない思いつき。`## Inbox` が主役 | 人（Obsidian モバイル / デスクトップ）+ `gtd-add` | `gtd-list` / `gtd-done` |
| **作業キュー** | resolver `project_task_store`（既定 `<project>/.claude/tasks.md`） | そのプロジェクトで次にやること | `context-save` + 人（`[x]` を付ける） | `context-load` |

**設計意図**: 書き手が知っている文脈の場所にだけ書く。モバイルには CWD が無いので捕捉箱へ、Claude は CWD を持つのでプロジェクトの作業キューへ書く。以前は 1 ファイルに両方が混在していたため、(a) 人が見て何が重要か分からない (b) `context-save` → tasks.md → `gtd-list` というスキル間の暗黙結合ができる、という 2 つの問題があった（2026-07-27 に分離）。

- **捕捉箱**: Obsidian Sync で全 PC・モバイル共有。**プロジェクト固有のタスクは置かない**
- **作業キュー**: 各リポジトリ内のローカルファイル。`~/`（ホームワークスペース）も 1 プロジェクトとして `~/.claude/tasks.md` を持つ。同期は各リポジトリの git 運用に従い、追跡しない場合はその PC 限りになる（PC を跨いで同じプロジェクトを触らない運用が前提）

## スキル別の責務

| スキル | 動詞 | ストア | 対象セクション |
|---|---|---|---|
| `gtd-add` | 追加（write） | 捕捉箱 | `## Inbox` |
| `gtd-list` | 表示（read） | 捕捉箱 | 全セクション |
| `gtd-done` | 完了化（write） | 捕捉箱 | `## Done` へ移動 |
| `context-save` | 追加・整理（write） | 作業キュー | `## Next` へ追加、`[x]` 行を `## Done` へ移動、古い Done を剪定 |
| `context-load` | 表示（read） | 作業キュー | `## Next` / `## Someday` |

`gtd-*` は捕捉箱しか触らず、`context-*` は作業キューしか触らない。**この境界を越えるスキルを作らない**（越えた瞬間、片方の環境で動かなくなる）。

## 捕捉箱のフォーマット

### セクション構造

```markdown
# Tasks

## Inbox
（未分類の新規タスク＝このストアの主役）

## Next
## Waiting
## Someday
（人が Obsidian 上で使いたければ使う。スキルは書き込まない）

## Done
（gtd-done で完了化した分）
```

セクションの順序と名称は固定。欠けている場合、スキルは該当セクションを追加してよい。

### タスク行

```
- [ ] #project/<name> タイトル [任意メタデータ]
```

- 先頭は `- [ ]`（未完了）または `- [x]`（完了）
- `#project/<name>` は**任意**。振り分け先が決まっているなら書く（後でその作業キューへ移すときの目印になる）。決まっていなければ付けない
- 任意メタデータ（`@key:value`）を末尾に追加してよい: `@since:2026-04-08`（Waiting 開始日）/ `@due:2026-04-15`（期限）/ `@captured-on-mobile`（モバイル捕捉）

### Done の特別ルール

Done に移動する際、タイトル先頭に完了日（`YYYY-MM-DD`）を付加する:

```markdown
- [x] 2026-04-09 #project/claude-config タスク管理設計の合意
```

## 作業キューのフォーマット

### セクション構造

```markdown
# Tasks — <project>

このファイルは `/context-save` が管理します。
手で `[x]` を付ける・行を足すのは OK（次回保存時に正規化されます）。

## Next
（次に着手するアクション）

## Someday
（条件待ち・保留。着手条件を先頭に書く）

## Done
（完了済み。2 週間で剪定）
```

冒頭の 2 行は**必ず入れる**。人と AI のどちらが管理しているかがファイルを開いただけで分かるようにするため。

### タスク行

```
- [ ] タイトル [任意メタデータ]
```

- `#project/<name>` タグは**付けない**（ファイルの場所がプロジェクトを表すため冗長。行を短くして人が読める状態を保つ）
- Done へ移す際は捕捉箱と同じく完了日を付ける: `- [x] 2026-07-27 タイトル`
- `## Someday` の行には保留理由・再開条件を先頭に置く（例: `[β 拡大判断時] ADR-0033 の起票要否を再評価`）

## タイトルの文字数規則（両ストア共通・MUST）

- **1 行 60-100 文字を中心とし、150 文字を絶対上限**とする
- 150 文字超のタイトルを書き込んではならない。`gtd-add` / `context-save` は書き込み前に文字数（タイトル本体部分）をチェックし、超過時は短縮するまで書き込みを中止する
- タスクストアは**タスク管理用**であり、進捗ログ / 判断メモ / コミット履歴を書く場所ではない。詳細は逃がす:
  - 進行中の作業状態・判断メモ → `.claude/context.md` / `.claude/progress.md`
  - 完了内容・コミット ID → git log / コミットメッセージ
  - 調査記録 → Obsidian Vault のノート（`20_log/`, `30_resource/` 等）
- 補足が必要なら短い修飾語のみ追加可（例: `(現 5/10、5/22 まで)`、`(詳細 context.md 7/24)`）

## モバイル運用（捕捉箱のみ）

### Obsidian モバイルアプリからのクイック追加

QuickAdd プラグインの `Quick Task` choice を Capture format `- [ ] {{VALUE}} @captured-on-mobile` で設定し、`## Inbox` 直後に追記する。iOS では Advanced URI 経由でショートカット.app から 1 タップ起動可能:

```
obsidian://adv-uri?vault=<iOS の Vault 名>&filepath=00_meta%2Ftasks.md&commandid=quickadd%3Achoice%3A<choice-id>
```

`@captured-on-mobile` メタにより、PC 側で `gtd-list` 実行時に「Inbox に N 件滞留中」として検出・警告される（GTD の「収集」と「整理」のフェーズ分離）。整理時にはこのメタを削除する。

### モバイルでの完了

タスク行先頭の `- [ ]` を `- [x]` にチェックするだけで完了扱い。日付付与は不要。次に PC で `gtd-list` を実行すると自動的に Done セクションへ移動する（完了日は gtd-list 実行日）。

### QuickAdd Capture format の改行必須

`format.format` の末尾に **改行を必ず含める**こと。改行がないと挿入位置直後の既存行と連結する（`insertTextAfterPositionInBody` は `text` の後ろに改行を補わない仕様。連続追加で 1 行に複数タスクが連結する事故が起きる）。UI 上では Capture format テキスト欄の末尾に **半角スペース 2 つ + Enter** で改行を入れる（半角スペースで UI 側の trim を回避でき、改行が `data.json` に保存される。参考: QuickAdd Issue #712）。

## 書き込みプロトコル（複数 writer・MUST）

両ストアとも Claude・Codex・人（エディタ / Obsidian）が同時に更新し得る。共通原則（保持・最小変更・再読込・競合停止・構造チェック・不明内容は削除しない）は `~/.claude/skills/shared/multi-writer.md` を SSOT とし、tasks.md 固有の適用を以下に定める。

### 基本

- 読み込み → 編集 → 書き戻す、の手順で操作する
- ファイルが存在しない場合、初期テンプレートを生成してよいのは捕捉箱では `gtd-add`、作業キューでは `context-save`
- **対象セクションのみを最小限 Edit する**。ファイル全体の Write は初期テンプレート生成時のみ許可
- セクション見出しの前後の空行は保持する。Done セクションは追記のみ（新しいものが上）
- **他 writer 由来の未知メタデータ・未知の行・コメント（`<!-- -->`）は削除せず保持する**

### 書き込み前チェック（MUST）

1. **書き込み直前の再読込**: Edit 適用の直前に再 Read する。最初の読取りと食い違う場合、**古いスナップショットを根拠にファイル全体を上書きしない**。差分が編集対象セクションと重ならなければ最新内容を基準に編集を組み直し、重なる・判断できない場合は自動編集を停止して競合を報告する
2. **重複セクションの検出**: 同名のセクション見出しが **2 回以上出現**する場合、Sync 競合等でファイルが二重化している疑いがある。この状態でセクションを anchor に編集すると意図しない側をサイレントに書き換えるため、**自動編集せずユーザーに警告**し、競合解消（1 組へのマージ）を促す
3. **重複タスクの追加禁止**: 同内容のタスクが既存セクションにある場合（部分一致で判定）、重複追加せず既存行の存在を報告してスキップする

### 書き込み後の構造チェック

書き戻した直後に、**セクション見出しが各 1 回のままか**だけを確認する。複数 Edit の巻き添えで見出しが欠落・重複しても Edit はエラーにならず、共有ファイルでは他 writer の内容ごと失われて巻き戻せないため。

それ以外は再確認しない: 編集の成否と追記行の実在は Edit が保証し（失敗すればエラーになる）、文字数は書き込み前チェックで担保済み。
