# stop-redundant — 出力の冗長性排除

AI 特有の「言い換えが多すぎる」「情報を全部出す」「読むのに疲れる」傾向を止める。

## 対象

対話応答 / コミットメッセージ / PR 説明 / コードコメント / レビュー所見。

**対象外**: 書籍・記事・技術文書の原稿。これは `japanese-doc-style` の `## 冗長の排除` 以下が担当する。原稿を書いているなら、まず japanese-doc-style に従い、本スキルは「AI の癖」の部分だけを足す。同じルールをここに再掲しない。

## ルール

### 1. 過剰に列挙するな

- 「A、B、C、D、E、F、G、H、I、J」と並べるな。「A〜J」とまとめろ。
- 思いつく限りの候補を書くな。絞れ。
  - Bad: 「GitHub Issue → Jira / Backlog / Linear / Redmine 等」
  - Good: 「GitHub Issue → Jira 等の課題管理」
- 選択肢の提示は別（CLAUDE.md「複数案 + 推奨案 + トレードオフ」）。**網羅の列挙**と**判断のための選択肢**を混同するな。

### 2. 知っている情報を全部書くな

- コンテキストに載っている情報を全部出力しようとする癖がある。本質的な情報だけ書け。
- 聞かれていない周辺知識を添えるな。関連するというだけで書くな。
- 「ちなみに」「なお」で始まる段落は、消して困らないか一度疑え。

### 3. 端的に表現しろ

- 強調した直後に後付けや但し書きをダラダラ続けるな。
  - Bad: 「対象は **機能追加のみ**。不具合対応・リファクタは対象外（別 SKILL で扱う想定）」
  - Good: 「対象は機能追加のみ」
- 同じ主張を言い換えて繰り返すな。一つの主張は一度だけ書け。
- 直前に書いたことを要約し直すな。
- 見出しと 1 行目で同じことを言うな。
- 表と本文で同じ内容を二度出すな。どちらか一方にしろ。

### 4. 定型で水増しするな

- 「〜について説明します」「以下に示します」のような予告を書くな。本文から始めろ。
- 作業の実況を書くな（重要な発見・方針転換だけ書く）。
- 末尾に「何か質問があれば」の類を付けるな。

## 削ってはいけないもの

冗長性の排除を理由に以下を落とすな。短さより正確さが優先する。

- **検証レベルの明示**（実行・実機で確認済み / コード・文書を読んで推論 / 未確認）
- **確認トリガーの提示**（変更内容 / 影響範囲 / 理由）
- 結論を変える**根拠と出典**、失敗時の**再現条件**
- ユーザーの判断が必要な**トレードオフ**

削って短くできるのは説明の量であって、事実の量ではない。

## 明示起動（`/stop-redundant`）

書いた文章を渡されたら、次の順で削る。

1. 段落単位で「消して意味が変わるか」を見て、変わらない段落を消す
2. 残った段落内で、上のルール 1〜4 に当たる箇所を削る
3. 「削ってはいけないもの」が落ちていないか照合する
4. 削除前後の文字数と、**何を削ったか**を 1 行で報告する（勝手に事実を落としていないことを確認できるようにする）
