# コンテキスト保存

現在のプロジェクトの作業状態を保存し、次回セッションで復帰できるようにする。

このスキルは **コア（`.claude/context.md` と `.claude/tasks.md` の保存、`.claude/handoff.md` の書き出しで完結・外部依存なし）** と **連携（progress.md / MEMORY / session-review が揃っていれば実行する任意処理）** に分かれる。**Obsidian は一切使わない**（捕捉箱 `~/ObsidianVault/00_meta/tasks.md` は `gtd-*` の担当で、本スキルは触らない）。連携の配線は `~/.claude/skills/shared/integrations.md`（resolver）で判定する。

frontmatter の `disable-model-invocation: false` は明示指定で、UserPromptSubmit hook（`context-save-reminder`、しきい値はスクリプト側で定義）の通知からモデルが自律実行することを許可する意図。手動 `/context-save` も可。

## コア（単独完結・連携なしで動く）

### 書き出し先

プロジェクトルートの `.claude/context.md`（**既存保持・最小変更**。既存ファイルがある場合は Edit ベースでセクション単位に更新し、テンプレートからの全体再生成はしない。ファイルが存在しない場合のみ `./template.md` から新規作成する）

context.md は Claude 専用ファイルではなく、**Codex 等の他 writer と共有する正本**である。書込みは `~/.claude/skills/shared/multi-writer.md` の書込みプロトコル（6 原則 + 再読込・競合停止・検証）に従う（MUST）。

#### プロジェクトルートの決定

1. `git rev-parse --show-toplevel` でリポジトリルートを取得
2. git リポジトリ外の場合は CWD をプロジェクトルートとする

#### ディレクトリの確認

- `.claude/` ディレクトリが存在しなければ `mkdir -p` で作成する

### 保存内容

セクション構成は `./template.md` のフォーマットに従う。ただし template.md は**新規作成時の雛形**であり、既存ファイルがある場合にテンプレートへ再流し込みしてはならない（既知セクションだけを最小限 Edit する。「既存ファイルの扱い」参照）。

#### 情報の収集

以下の情報を収集してテンプレートに埋める：

- **project**: リポジトリのディレクトリ名（`basename` で取得）
- **git リモート URL**: `git remote get-url origin`（取得できない場合は空欄）
- **現在のブランチ**: `git branch --show-current`
- **git 状態**: `git status --short` の要約
- **直近のコミット**: `git log --oneline -5`
- **プロジェクト概要**: セッション中の作業内容から簡潔にまとめる
- **進行中の作業**: 現在取り組んでいるタスクや未完了の作業。**各 entry は `- YYYY-MM-DD（任意の補足）: 内容` 形式で書く**（日付プレフィックスがローテーションの基準。古い entry は「## 進行中の作業のローテーション」セクションで自動削除）。既存ファイルの entry がこの形式になっていない場合は、保存時に Claude が当時の日付を推定して付け直す（git log の日付・本文中の日付・前後の文脈から推定。推定できなければ「YYYY-MM-DD不明」のままにして保守的に残す）
- **判断メモ**: セッション中に行った重要な判断とその理由（プロジェクト固有の判断は context.md に残す。プロジェクトをまたいで再利用される普遍知見の MEMORY.md 昇格は「## 連携」の連携2 で扱う）
- **重要ファイル**: 作業に関連する主要ファイル（プロジェクトルートからの相対パス）
- **関連リポジトリ履歴**（ホームワークスペース用・任意）: `chezmoi source-path` でパスを取得し、`git -C <path> log --oneline -n 5` と `git -C <path> remote get-url origin` を「関連リポジトリ」セクションに埋め込む。コマンド失敗時（chezmoi が無い等）はスキップ

**次のステップについて**: 次回セッションで着手すべきタスクは context.md には書かない。同じ `.claude/` 配下の作業キュー `tasks.md` に保存する（後述「タスクの保存」）。

### 既存ファイルの扱い

書き出し先に既存ファイルがある場合：
- まず既存ファイルを全文読み込む（= 書込みプロトコルの「初回読取り」）
- **既知セクションのみ**を最新情報で更新する: `## プロジェクト概要`（引き継ぎつつ必要なら更新）/ `## 現在の状態` / `## 進行中の作業` / `## 判断メモ` / `## 関連リポジトリ` / `## 重要ファイル` / `## メモ`、および frontmatter の既知キー（`updated` 等）
- **未知の frontmatter キー・見出し・フィールド・本文は削除・上書きせず無条件保持する**（Codex 等の他 writer の追記。詳細は `shared/multi-writer.md`）。`tags: claude-context` は新規作成時テンプレートの既定値であり、他 writer が作ったファイルに無くてもエラーにせず、追加もしない
- 他 writer が書いた有効な内容を、文体正規化だけを目的に書き換えない。`updated_by: claude` のような writer 識別フィールドを追加しない
- `updated` の日時を更新する。**日付だけでなく保存時の実時刻まで書く**（`2026-08-18T10:43:00` のように。`T00:00:00` 固定にしない）。UserPromptSubmit hook `context-save-reminder`（`~/.claude/scripts/context-save-reminder.ps1`）は **frontmatter の `updated` 値**（ファイルの mtime ではない）を基準に経過分を測るため、0 時固定で書くと保存直後でも「N 分経過しています」が再発火し、同一セッションで無駄な保存を繰り返すことになる
- 過去に `## 次のステップ` セクションが残っている場合は**削除**する（タスクは `.claude/tasks.md` に一本化、context.md には書かない。lossy 処理③ — 「タスクの保存」で作業キューへ移した後、または内容が作業キュー/本文に反映済みであることを確認してから削除する）
- **同一セッションで 2 回目以降の保存になる場合は差分更新でよい**（hook 起因の自律実行 → 後から `/session-save` を明示起動、のように 1 セッションで複数回走るのは正常）。1 回目以降に増えた分だけを既知セクションへ追記し、`updated` を更新する。**当日 entry の再圧縮・ローテーションの再実行はしない**（当日分は compress-on-complete の対象外で、2 回目に走らせても縮まないうえ Edit の回数だけ増える）

### 書込みプロトコル（複数 writer・MUST）

context.md への書込みは `shared/multi-writer.md` の共通プロトコルに従う：

1. 初回読取り（上記「既存ファイルの扱い」の全文 Read）
2. 変更を既知セクション単位の Edit として構成（ファイル全体の Write は新規作成時のみ）
3. **書込み直前に再 Read** する
4. 初回読取りから内容が変化していた場合（別プロセス / Codex が更新した可能性）: 差分が編集対象セクションと重ならなければ最新内容を基準に Edit を組み直して続行、重なる・判断できない場合は**自動書込みを停止**し差分を提示してユーザーに競合報告
5. Edit 適用
6. 書込み後の構造チェック: 見出し集合・frontmatter キー集合が編集意図（lossy 処理の明示分）以外で減っていないかだけを見る（編集箇所が適用されたか自体は Edit が保証するので再確認しない）

#### lossy 処理の明示列挙

情報を失う処理は以下の 4 つのみ。いずれも**既知フォーマットに一致した対象のみ**に適用し、パースできない entry・形式不明の entry は保守的に残す。実行時は通常更新と区別して件数を報告する：

1. `## 進行中の作業` の 14 日ローテーション（後述）
2. 完了 entry の圧縮 compress-on-complete（後述）
3. 旧 `## 次のステップ` セクションの削除（上記）
4. `## 関連リポジトリ` のコミットリストの最新 5-6 件への丸め

### 進行中の作業のローテーション

`## 進行中の作業` セクションは時系列で追記されるため放置すると肥大化し、context-save / context-load の token 消費・処理時間が増え続ける。保存時に古い entry を機械的に削除して定常サイズに保つ。

#### ルール

- **削除対象**: entry 先頭の日付（`- YYYY-MM-DD...` プレフィックス）が **今日から 14 日より古い** もの
- **最低保証**: 削除後の entry 数が 3 件未満になる場合、新しい順に 3 件は必ず残す（時系列の連続性を保つための保険）
- **削除した本文の正本は外部ログ**（作業ログ・git log）。本スキルは外部ログの存在を前提とせず削除だけを責務とする。外部ログが無い環境では閾値を伸ばす判断をユーザーに委ねる

#### 手順

1. 既存 context.md の `## 進行中の作業` セクションを抽出
2. トップレベルの `- YYYY-MM-DD` で始まる行を entry の境界として分割する（子の箇条書きやインデントされた行は直前の entry の一部として保持）
3. 各 entry 先頭の日付（`- YYYY-MM-DD` 部分のみ、`（午後・完了）` 等は無視）をパースし、今日との日数差を計算
4. 「14 日以内 (= 今日 − 14 日 以降)」の entry に加え、それでも 3 件未満なら新しい順に 3 件まで補充
5. 残った entry を新しい順で並べ、書き戻す
6. 削除した entry がある場合は、書き戻し後に「（古い N 件はローテーションで削除）」程度の 1 行注記を末尾に追記してもよい（任意）

### 完了 entry の圧縮（compress-on-complete）

14 日ローテーションは「消す」だけで「痩せさせる」段階がないため、完了済み entry を「完了 → 圧縮 →（14 日後）削除」のライフサイクルに乗せる。

#### ルール

- **対象**: 補足括弧に完了状態（`完了` / `クローズ` / `残なし` など）を含む entry のうち、**日付が今日でないもの**。このセッションで書いたばかりの詳細は次セッションの復帰材料なので当日分は触らない（圧縮は 1 保存周期遅れる）
- **圧縮形式**: `- YYYY-MM-DD（完了）: <1〜2 文の成果サマリ>。残: <未消化項目あれば 1 行>（詳細: <entry 内の既存ポインタ — 作業ログ / commit / PR>）`
- **サイズ**: 目安 200 文字、絶対上限 300 文字
- **保持必須 4 点**: ①日付プレフィックス ②完了状態 ③残（未消化）項目 ④entry 内に既にある参照ポインタ（作業ログパス・commit ID・PR 番号）。経緯・手順・数値・ファイル一覧は捨てる（詳細の正本は作業ログ・git 履歴）
- **保守則**: 完了マーカーが曖昧な entry（進行中とも読める・一部完了など）は圧縮しない
- 残項目は作業キュー（`.claude/tasks.md`）へ保存済みでも圧縮行に 1 行保持する（見落とし防止の二重化）
- **1 回の保存で圧縮するのは文字数の多い順に 3 件程度まででよい**。残りは次回以降か `/session-review` へ送ってよく、部分実行は失敗ではない。報告時に「今回圧縮 N 件・未圧縮 M 件」と件数を明示する（残り候補が全て目安サイズ内なら「今回 0 件」も正常）
- **【entry 境界の保護｜MUST】置換範囲は「対象 entry の見出し 〜 次の entry 見出し」に限定する**。終端は次 entry の日付見出し（`^- \d{4}-\d{2}-\d{2}`）か `## ` 見出しにし、**entry 内の項目番号（`② ...` 等）を終端に使わない**（同じ番号が後続 entry にも現れ、間の entry を巻き込んで消す。2026-07-27 に実発生）。適用前に置換範囲の文字数を出力し、想定（数百字）から桁が外れていたら中断する。書込み後は entry 件数が減っていないことを確認する
- **複数 entry をまとめて置換するときは「行番号 + プレフィックス assert」で組む**: ①ファイルを行配列で読む ②置換・削除する各行が期待する見出しで始まることを assert する（外れたら停止＝インデックスずれの検出） ③残す entry は転記せず元の行を参照して新配列を組む ④別ファイルへ書いて見出し集合・entry 件数・バイト数の前後比較を出し、想定どおりなら apply する。Edit の完全一致置換より安全で 10 件規模でも 1 回で終わる

### サイズアラート

保存完了後にファイル全体のサイズをチェックし、肥大の早期警報を出す（判断メモの肥大アラートと同じ「アラートのみ・自動編集しない」設計）。

- `wc -c` 相当で **12,288 bytes（12KB）超** なら次の 1 行アラートを表示する:
  - `⚠️ context.md が N KB あります。完了 entry の圧縮漏れ・重要ファイル表の陳腐化を確認してください`
- 判断メモアラートと両方発火する場合は 2 行とも表示してよい（対象セクションが異なるため置換しない）

#### アラート発火時の対応手順（ユーザーが「対応して」等で対応を求めたとき）

1. **主犯を実測で特定する**（推測で削らない）: セクション別サイズを計測し、太いセクションを名指しする
2. 主犯別の対処: **完了 entry の圧縮漏れ** → その場で圧縮形式へ変換 / **`## 現在の状態` の肥大** → 下記の統合ルールで畳む / **重要ファイル表の陳腐化** → 参照先の存在確認 + SKILL.md 等の正本と重複する説明文の削り提案 / **判断メモの肥大** → `/session-review` の判断メモ圧縮フェーズへ委譲
3. 超過が**当日 entry 由来の一時的なもの**（翌日以降の保存で compress-on-complete により下回る見込み）なら、削らず「様子見」を第一候補として提示する
4. **自然減で消える分は圧縮しない**: `## 進行中の作業` の古い完了 entry は数日内にローテーションで消えるので、圧縮の手間が無駄になる。残り日数を数えてから対象を選ぶ

#### `## 現在の状態` の統合（compress-on-complete の対象外なので手動で畳む）

`## 現在の状態` には痩せさせる仕組みが無く、完了した経緯が bullet 単位で積み上がってサイズアラートの主犯になりやすい（2026-07-29 degcloud: 6 行で 5.8KB）。アラート対応時は次の 2 つを適用する:

- **決着した並列項目は 1 行へ集約する**: マージ済み PR・削除済みブランチ・解消済み OI のような「もう分岐しない」項目は、個別 bullet をやめて識別子（PR 番号・commit・ホスト名）だけ残した 1 行にまとめる
- **完了した構築・調査は成果 1 行へ**: 経緯（失敗 → 原因特定 → 対処）は判断メモか作業ログが正本なので、現在の状態には**今後も参照する値**（principalId・URL・Secret 名・残 OI）だけを残す

いずれも「次に読む人が判断に使う値」を落とさないことが条件。

### 判断メモの肥大アラート

`## 判断メモ` セクションは時間でローテーションしない（普遍知見の昇格判断が要るため機械削除できない）。代わりに、保存時に**エントリ件数とセクションのバイト数の両方**をチェックし、肥大したら圧縮を促すアラートを出す。

#### ルール

- `## 判断メモ` のトップレベルエントリを数える。先頭行は **`- ` 箇条書き** / **`**見出し**（日付）:` 段落**（`:` の直前に括弧が入りうる） / **`### ` 見出し** の 3 形式があり、**いずれも 1 エントリとして数える**（子のインデント箇条書き・`> ` 引用行は数えない）。1 形式だけを数えるとその形式を使わない context.md で恒久的に 0 件になりアラートが不発火する（yoroi / kabuto / degcloud で 3 回発生）。**未知の形式が出たら「0 件」と報告する前にセクションを目視する**
- **件数が 15 件を超えている**、**または `## 判断メモ` セクション単体が 6,144 bytes（6KB）を超えている**場合、context-save 完了後に次の 1 行アラートを表示する（バイト数側で発火したときは件数でなくサイズを書く）:
  - `⚠️ 判断メモが N 件あります。昇格・統合・削除での圧縮を検討してください`
  - `⚠️ 判断メモが N KB あります（M 件）。1 件あたりが長いので昇格・統合・ポインタ化での圧縮を検討してください`
- 件数が閾値未満でも 1 エントリが数百字あればセクションだけで context.md の大半を占める（toto-predictor で 12 件 11KB = 全体の 41%）。エントリ 1 件が 500 字を超えるのは、詳細を docs / memory / docstring へ逃がしてポインタだけ残すサイン
- **アラートは常に 1 行**。連携3 が発火する場合は、この汎用 1 行を出さず連携3 の文言に**置換**する（2 行出さない）
- アラートを出すだけで、本スキルは判断メモを削除・編集しない（仕分けは判断を要するため別途。委譲先の案内は連携3）

### タスクの保存（作業キュー）

セッション中に発生した「次に着手すべきアクション」を、プロジェクトの作業キュー `project_task_store`（既定 `<project-root>/.claude/tasks.md`）に保存する。あわせて、人が `[x]` を付けた行を Done へ整理する。**フォーマット規約は `~/.claude/skills/shared/tasks-format.md` の「作業キューのフォーマット」が SSOT**（本 SKILL.md で再掲しない）。

Obsidian Vault の捕捉箱は**参照しない**。捕捉箱に落ちた思いつきをプロジェクトへ振り分けるのは人の作業（`gtd-*` の担当）。

#### 手順

1. resolver から `project_task_store` を解決する（空・未設定なら本節を skip し、context.md の保存は続行）。プロジェクトルートの決め方はコア冒頭と同じ
2. ファイルが無ければ tasks-format.md の「初期テンプレート（作業キュー）」で新規作成する（見出し 3 つ + 冒頭の管理注記）
3. **`[x]` 行の Done 整理**: `## Next` / `## Someday` の `- [x]` 行を検出し、`- [x] YYYY-MM-DD タイトル` に正規化して `## Done` の先頭へ移す（既に日付付きならそのまま使う＝冪等）。人がエディタや Obsidian でチェックしただけの行を回収する工程
4. **Done の剪定**: `## Done` から 2 週間より古い行を削除する（しきい値は `date -d "2 weeks ago" +%Y-%m-%d`。日付を抽出できない行はスキップ＝保守的に残す）
5. セッション中に合意された「次にやること」を `## Next` に `- [ ] タイトル` 形式で追記する（条件待ち・保留は `## Someday` に、着手条件を先頭に置いて追記）。**書く前に tasks-format.md の「Next に置くのは『着手して終わる行為』だけ」を満たすか確認する**＝観測結果・判断材料・数値の記録は Next でなく context.md へ書く
6. **【文字数ガード｜MUST・書き込み前】** 各行のタイトル文字数を**実際に数え**、150 文字を超える行はそのまま書き込まない。超過時は詳細（手順・根拠・数値・commit ID・経緯）を context.md / docs へ逃がし、参照ポインタだけ残す（例: `(詳細 context.md 7/27)`）。それでも収まらなければタスクを複数行に分割する
7. **【保存時計測｜MUST】書き込み後に `## Next` / `## Someday` の全行を計測し、150 文字超が残っていれば件数と行番号を報告する**（手順 6 は「これから書く行」にしか効かず、人が手で足した行や過去の保存で入った行は素通りする）。超過行の短縮は**その場でやらずユーザーに提示する**（既存タスクの要約は情報を落とす判断を伴う）
8. **【件数アラート】書き込み後に `## Next` の行数を数え、15 件を超えていたら 1 行で報告する**: `⚠️ Next が N 件あります。タスクでない行（観測・判断材料）が混ざっていないか棚卸しを検討してください`。性質がメモの行は短いまま溜まる（degcloud で 34 件）ので、文字数ガードでは拾えない。**棚卸しはその場で実行せず提示だけする**
9. 既に同内容のタスクがある場合は重複追加しない（部分一致で判定）
10. 書き込み直前に再 Read し `shared/multi-writer.md` の競合検出に従う。書き戻し後は**セクション見出しが各 1 回のままか**だけ確認する
11. 実行内容を報告する（追加 N 件 / Done 昇格 M 件 / 剪定 K 件 / 文字数超過 L 件 / Next 件数）

#### 追加対象の判断基準

- 明確に「次にやること」として合意されたアクションのみ追加する
- 推測や「やったほうがいいかも」レベルは追加しない（未分類の思いつきは捕捉箱の担当＝`/gtd-add`）
- タスクが発生していない場合は追加をスキップしてよい（手順 3・4 の整理は実行する）

### 引き継ぎメモの書き出し（handoff.md）

`{project-root}/.claude/handoff.md` に「**今この瞬間、他のエージェントへ作業を渡すとしたら何を伝えるか**」を書く。Claude で行き詰まったら Codex へ、Codex で行き詰まったら Claude へ、という往復（agent handoff）を成立させるための節。

**なぜ context.md と分けるか**: 引き継ぎで相手が必要とする「何を試してなぜ駄目だったか（negative results）・仮説・再現手順」は翌週には無価値になる揮発情報で、恒久ファイルの context.md に混ぜるとローテーション判断が増える。責務を分けて別ファイルにし、書き出しは context-save に内包する（コマンドを 2 つに割ると毎回どちらを使うかの判断が発生する）。

**毎回書く**。「行き詰まった時だけ」にすると肝心な時に書かれていない失敗モードを作る。毎回書けば余計な情報が出るだけで済む。

#### ファイル仕様

```markdown
---
from: claude
at: 2026-08-25T10:12:00
topic: <この作業を 1 行で>
---

## 現状（どこまで動くか）
## 未解決・詰まっている点
## 試して駄目だったこと
## 現在の仮説
## 再現手順
## 未コミットの変更
## 次の一手
```

- `from` は書き手の識別子（Claude なら `claude`、Codex なら `codex`）。**context.md 側には writer 識別フィールドを足さない**規約（`shared/multi-writer.md`）と矛盾しないよう、識別子を持つのはこの handoff.md だけに閉じる。読み手が「自分が書いたもの」と「相手からの引き継ぎ」を区別するために必須
- `at` は保存時の実時刻まで書く（`T00:00:00` 固定にしない）
- **各セクションは空欄で残さず、該当が無ければ `- なし` と明記する**。空欄だと読み手が「本当に無い」のか「書き忘れ」なのかを区別できない
- `## 未コミットの変更` には `git status --short` の出力を載せる。Claude と Codex は同じ working tree を共有するので**ファイル自体は自動的に渡っている**（stash も WIP コミットも不要）。ここに載せるのは、相手が「この差分は自分が壊したのか」で迷わないためのスナップショット
- 全体で 1,500 字を目安にする。超えるなら詳細は context.md か作業ログへ逃がし、ここにはポインタだけ残す

#### 手順

1. プロジェクトルートを決定する（コア冒頭と同じ）
2. `git status --short` を取得する
3. 既存の `handoff.md` があれば Read する
4. 上記フォーマットで**全面上書き**する
5. 書き出した旨を 1 行報告する（`引き継ぎメモを更新（未解決: あり/なし）`）

#### 全面上書きの扱い（multi-writer プロトコルの例外）

handoff.md は **1 件だけを保持する揮発ファイル**であり、`shared/multi-writer.md` の「ファイル全体の Write は新規作成時のみ」の対象外とする（全面上書きが仕様。上書きは lossy 処理だが、context.md の lossy 処理 4 つとは別枠でここに明示する）。

ただし相手 writer の引き継ぎを黙って消さないよう、次のガードを置く:

- **既存 handoff.md の `from` が自分と異なる場合**、新しい handoff の末尾に 1 行だけ痕跡を残す:
  `> 前の引き継ぎ（from: codex, at: 2026-08-25T09:40）: <topic>`
- ガードは**ブロックしない**（確認を求めない）。context-save は hook から自律実行されるため、毎回停止すると保存自体が回らなくなる。情報の完全消失だけを防げばよい

## 連携（任意・対象があれば実行）

**連携の前提確認**: `~/.claude/skills/shared/integrations.md` を Read する（無ければ全キー未設定とみなす）。各連携の ［参照キー］ を resolver の「参照規約」で判定する。**(a)→(b)→(c) を上から評価し最初に真の分岐を採る**:
- **bool 系キー**（progress_map / memory_promotion）: probe 判定なし。`on` → 実行 / `off`・未設定 → skip

本スキルの連携に path 系キー（`task_store` 等）は無い。**Obsidian Vault は参照しない**（作業キュー `.claude/tasks.md` はコアの担当、捕捉箱は `gtd-*` の担当）。

いずれの連携も skip 可能で、「## コア」の成否には影響しない。

### 連携1: 進捗マップの更新 ［参照キー: progress_map］

`progress_map` が on で、プロジェクトルートの `.claude/progress.md` が存在する場合、セッション中の作業を反映してチェックボックスを更新する。`.claude/progress.md` はローカル管理（`.gitignore` 対象）で、各開発者が個別に保持する。

#### 手順

1. `{project-root}/.claude/progress.md` を Read で読む
   - `progress_map` が off → 連携1 を skip
   - 存在せず、かつ `{project-root}/CLAUDE.md` に `## 進捗マップ` セクションがある場合は、後方互換として CLAUDE.md 側を対象にする（旧形式）
   - どちらもない場合はスキップ
2. セッション中に完了した作業に対応するチェックボックスを `- [ ]` → `- [x]` に更新する
3. 新たに着手が見えたタスクがあり、進捗マップに項目がない場合は適切な位置に `- [ ]` で追加する
4. `最終更新:` の日付を当日に更新する
5. **書き込み直前に再 Read** し、手順 1 の読取りから内容が変化していないか確認する（`shared/multi-writer.md` の競合検出。変化が編集対象行と重なる・判断できない場合は自動書込みを停止してユーザーに報告）
6. Edit ツールで対象行のみ書き戻し、書き込み後に再 Read して編集箇所と項目の保持を検証する

#### ルール

- **ファイル全体を再生成しない**。対象チェックボックス行・追加項目・`最終更新:` 行のみを Edit で最小変更する
- progress.md は Codex 等の他 writer と共有する正本。**未知の項目・他 writer が追加した項目・見出しは削除せず保持する**
- 進捗マップの構造（セクション番号・見出し）は変更しない
- チェックの付け外しと項目の追加のみ行う
- 既にチェック済みの項目を外さない（他 writer が付けたチェックも外さない）
- 不確かな場合はチェックしない（次回セッションで確認）

### 連携2: 判断メモの MEMORY.md 昇格提案 ［参照キー: memory_promotion］

`memory_promotion` が on の場合、`## 判断メモ` のうちプロジェクトをまたいで再利用される判断（コミット粒度ルール、ツール固有の罠、ライブラリ選定基準など普遍的知見）について、MEMORY.md（`feedback_*.md` / `user_*.md` / `reference_*.md`）への昇格を提案する。プロジェクト固有の判断は context.md に残す。判断メモは時間でローテーションしないため、context.md に書き続けると肥大化の主要因になる点を踏まえて仕分けを促す。

- `memory_promotion` が off / 未設定 → 連携2 を skip（昇格提案を出さない）
- 昇格の実書き込みは本スキルでは行わず、提案のみ（ユーザー判断 or MEMORY 管理フローに委ねる）

### 連携3: 判断メモ圧縮の委譲案内 ［参照キー: session-review スキルの有無］

コアの「判断メモの肥大アラート」が発火した（15 件超）とき、`session-review` スキルが利用可能なら、コアの汎用 1 行を次の文言に**置換**する（追記しない＝アラートは常に 1 行）:

- `⚠️ 判断メモが N 件あります。/session-review の「判断メモ圧縮」フェーズで昇格・統合・削除を検討してください`

`session-review` が無い環境では、コアの汎用アラート文言のままにする（委譲先を案内しない）。

## 注意事項

- パスはプロジェクトルートからの相対パスで記録する（マシン非依存）
- git リモート URL を frontmatter に記録する（マシン間でのプロジェクト同定用）
- セッション全体を振り返ってからまとめること
- PR 番号・Issue 番号など外部の可変識別子を記録する場合は **ブランチ名・タイトル・最終確認日** も併記する（番号だけだと次セッションで中身を誤認する）
- **PR の状態（draft / ready / OPEN / MERGED・承認件数・マージ可否）は他人の操作で変わる**。必ず「いつ時点か」とセットで書き（例: 「07-24 時点で draft」）、次セッションでは `gh pr view` で実査してから判断する前提にする（degcloud で 2 回、記録と実態が食い違った）
